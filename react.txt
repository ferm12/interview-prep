What kind of problems are best addressed with React?

✅ Problems Best Addressed with React
    1. Complex, Interactive UIs
        ◦ React makes it easier to build and manage complex UIs where elements update frequently (e.g., dashboards, forms, live feeds).
    2. Reusable Components
        ◦ Projects that benefit from a modular architecture where UI elements (like buttons, forms, modals) are reused across multiple pages or features.
    3. Single-Page Applications (SPAs)
        ◦ Apps that load once and dynamically update content without reloading the page (e.g., Gmail, Trello, Notion).
    4. Real-Time Data Updates
        ◦ Applications that fetch and display changing data (e.g., stock tickers, chat apps, notification systems).
    5. Client-Side Rendering (CSR) + Server-Side Rendering (SSR)
        ◦ With frameworks like Next.js, React supports both CSR and SSR for better performance and SEO.
    6. Scalable Frontends
        ◦ Projects that need to grow over time, with multiple developers working on different parts of the UI without conflicts.
    7. Cross-Platform Development
        ◦ React Native allows code reuse between web and mobile apps, making React ideal for teams building for multiple platforms.




What kind of problems are better addressed by frameworks other than React?
🚫 Problems Better Addressed by Frameworks Other Than React
1. Full-Stack Out of the Box
    • Better Option: Next.js, Nuxt.js (Vue), Laravel, Rails
    • Why: React is just the view layer. If you need routing, SSR, APIs, and state handling all baked in, a full-stack framework is more efficient.
2. Highly Opinionated Architecture
    • Better Option: Angular
    • Why: Angular provides a strict structure, dependency injection, TypeScript-first support, and out-of-the-box solutions for routing, HTTP, forms, and testing. Ideal for large teams that benefit from convention over configuration.
3. Lightweight, Simpler Apps
    • Better Option: Vue.js, Svelte
    • Why: For small to medium apps with less complexity, Vue or Svelte can offer faster ramp-up time, smaller bundles, and more intuitive templating.
4. Mobile-First Native Applications
    • Better Option: Flutter
    • Why: React Native is great for cross-platform apps, but Flutter provides better performance and more control over native UI when building mobile apps from scratch.
5. Server-Heavy or Monolithic Backends
    • Better Option: Django, Ruby on Rails
    • Why: When most of the logic is server-side and the frontend is minimal, a traditional monolithic framework with templating (e.g., Django’s Jinja2) may be more efficient.
6. Static Site Generation Without a SPA
    • Better Option: Hugo, Jekyll
    • Why: For blogs or documentation sites, static site generators offer lightning-fast performance without the overhead of a JS framework.

How does components communicate in react 

🔥 1. Parent → Child (Top-Down)
Method: Props
This is the most common and recommended way.
Example:
function Parent() {
  return <Child message="Hello" />;
}

function Child({ message }) {
  return <p>{message}</p>;
}
The parent sends data to the child using props.

🔥 2. Child → Parent (Bottom-Up)
Method: Passing callback functions from parent to child
The parent provides a function; the child calls it.
Example:
function Parent() {
  const handleClick = (value) => {
    console.log("Child clicked", value);
  };

  return <Child onChildClick={handleClick} />;
}

function Child({ onChildClick }) {
  return (
    <button onClick={() => onChildClick("Hello parent!")}>
      Click Me
    </button>
  );
}
This allows the child to send data or events back to the parent.

🔥 3. Sibling → Sibling
Siblings can’t talk directly; they communicate via their closest common parent.
Methods:
Lift state up to the parent
Use a global store (Context, Redux, Zustand, jotai)
Example using shared parent:
function Parent() {
  const [value, setValue] = useState("");

  return (
    <>
      <SiblingA setValue={setValue} />
      <SiblingB value={value} />
    </>
  );
}

TREE SHAKING
Tree shaking is the bundler dropping unused exports from the JS you ship. React does not do it. Webpack, Rollup, esbuild, and Vite do, in a production build, using static ES import/export.
It is dead-code elimination, not code splitting. React.lazy / import() splits when code loads. Tree shaking deletes code you never import.

using setTimeout
useEffect(() => {
  const id = setTimeout(() => {
    search(query);
  }, 1000);
  return () => clearTimeout(id);
}, [query]);
Every new query clears the previous 1000ms wait and starts over. Only the last pause actually searches.

Cleanup fn runs before the next effect (and on unmount). The slow response is dropped. 
The network request may still finish.
Each effect run closes over its own cancelled. That is why the old request cannot flip the new flag, 
and the new request is not cancelled by the old cleanup.

Reconciliation is how React decides what to change in the UI after a render. You return a new element tree; React diffs it against the previous tree and updates only what changed in the DOM (or native views).

It is not “wipe the screen and rebuild.” It is diff + patch.

The loop
State/props change → React renders (calls your function, gets new JSX).
Reconcile: compare new tree vs old tree.
Commit: apply the minimal DOM updates (insert, delete, update attributes, move).
Render can be thrown away (Concurrent Mode). Commit is what the user sees.

Lifting state means moving state up to the closest parent that needs it, then passing data down as props and updates down as callbacks. Siblings never share useState directly.

Here two children both need the same query: the input writes it, the list reads it. The state lives in FilterableList, not in SearchBox.


function FilterableList({ items }: { items: string[] }) {
  const [query, setQuery] = useState("");
  const visible = items.filter((item) =>
    item.toLowerCase().includes(query.toLowerCase())
  );
  return (
    <>
      <SearchBox query={query} onQueryChange={setQuery} />
      <ResultList items={visible} />
    </>
  );
}
function SearchBox({
  query,
  onQueryChange,
}: {
  query: string;
  onQueryChange: (value: string) => void;
}) {
  return (
    <input
      value={query}
      onChange={(e) => onQueryChange(e.target.value)}
      placeholder="Filter"
    />
  );
}
function ResultList({ items }: { items: string[] }) {
  return (
    <ul>
      {items.map((item) => (
        <li key={item}>{item}</li>
      ))}
    </ul>
  );
}
